## Why this lab

You want the same private object available in Sydney and Auckland. A
[Pulp](https://pulpproject.org/)-style HTTP repo can do that too, but you end up
running a server and owning the network path. Here S3 does the heavy lifting:
publish once in Sydney, let <Tooltip term="crr" label="replication" /> copy to
Auckland, and have each consumer VPC read its **local** bucket through a
<Tooltip term="gateway-vpce" label="gateway VPC endpoint" />.

Once the object has replicated, Auckland keeps reading Auckland if Sydney is
down (and the other way around). That is not full multi-Region
<Tooltip term="ha" label="HA" /> though. You still publish to Sydney,
replication is async so <Tooltip term="rpo" label="RPO" /> is not zero, and
anything in a failed Region is still down.

  </Card>
  <Card title="Publish and prove" icon="approve-check">
    Upload in Sydney, wait for the replica, curl from an SSM-managed EC2.
  </Card>
  <Card title="Tear down" icon="close">
    Empty the versioned buckets and delete the lab with <code>demo.sh down</code>.
  </Card>

| Expectation | Notes |
| ----------- | ----- |
| Same object key | Different regional hostnames |
| Cross-region reads | Via the replica, not cross-Region PrivateLink |
| Cost while running | S3 + replication transfer + probe EC2 / SSM endpoints |

<Aside type="caution">
  This lab costs money until you tear it down. Destroy the consumers before you
  empty the shared buckets if you created SSM interface endpoints.
</Aside>
